# 第 07 章:完整的開發與測試流程

> 前面幾課教你「怎麼寫」,這一章教你「怎麼有紀律地開發與驗證」。
> 養成這套流程,專案變大時才不會手忙腳亂。

---

## 7.1 開發流程總覽

一個嵌入式功能從無到有,通常會走這個循環:

```
  ① 想清楚要做什麼(需求)
  ② 設計:用到哪些腳位 / 周邊 / SFR?
  ③ 寫程式
  ④ 編譯          make
  ⑤ 主機端測試     make test        ← 在電腦上測「純邏輯」
  ⑤.5 指令級模擬   s51 …(選用)    ← 在電腦上跑真正的 HEX
  ⑥ 燒錄          make flash
  ⑦ 實機測試:行為對嗎?
  ⑧ 版本控制:git commit / push(留下里程碑)

  迴圈:④⑤⑦ 任一步失敗(編譯錯 / 測試不過 / 實機行為不對),
        就回到 ③ 修改,再往下跑一次。
```

重點精神:**把問題「往左邊」趕**。能在編譯期發現的錯,就不要留到燒錄後;
能在電腦上(第 ⑤ 步)測的邏輯,就不要每次都燒到板子才驗證。越左邊,除錯越快越便宜。

---

## 7.2 第 ④ 步:編譯

```bash
cd c/03-timer
make
```

- 成功 → 產生 `main.hex`。
- 失敗 → 編譯器會指出**檔名:行號**和錯誤原因。先解決**第一個**錯誤再重編(後面的錯常常是被第一個連累的)。

一次檢查「所有範例」有沒有被改壞(例如你動了共用的 `N76E003.h`):

```bash
make          # 在專案根目錄:編譯全部 10 個範例
```

---

## 7.3 第 ⑤ 步:主機端測試(在電腦上測純邏輯)

微控制器程式不能直接在 PC 跑,但**不碰硬體的計算邏輯可以**。我們把這種邏輯抽到
[`tools/host_test/logic.c`](../tools/host_test/logic.c),用電腦的 `gcc` 編譯、用 `assert` 驗證:

```bash
cd tools/host_test
make test
```

會看到每筆「輸入 → 實際輸出 → 期望輸出」,全部符合才算通過。

這裡跑的其實有兩組測試:

| 測試檔 | 測什麼 | 受測原始碼 |
|--------|--------|-----------|
| [`test_logic.c`](../tools/host_test/test_logic.c) | 數字轉字串、ADC 換算電壓 | `tools/host_test/logic.c` |
| [`test_fsm.c`](../tools/host_test/test_fsm.c) | 第 7 課的狀態機(30 項) | **`c/07-fsm/fsm.c`** ← 燒進晶片的同一份 |

第二組特別值得注意:受測的是**真的會被 SDCC 編進 N76E003 的那份原始碼**,
不是另外抄一份。這是因為第 7 課刻意把狀態機寫成零硬體相依(見
[`11-狀態機.md`](11-狀態機.md) §11.5)。它還包含「車道綠燈與行人綠燈絕不同時亮」
這類**安全不變式 (invariant)** 測試 —— 用肉眼看號誌很難保證的事,程式幾毫秒就掃完。

另外第 7 課還附一個**模擬器**,可以餵不同輸入、把輸出畫成表格看:

```bash
make sim        # 在專案根目錄
```

**為什麼值得這樣做?**
- 快:不用燒錄,一秒內知道對錯。
- 可重複:邊界值(0、最大值)每次都自動檢查,不怕改壞。
- 這就是「單元測試 (unit test)」的精神 —— 把大問題切成可獨立驗證的小塊。

> 設計程式時有個好習慣:**盡量把「演算法」和「硬體操作」分開**。
> 例如「把 ADC 值換算成電壓」是演算法(可測),「讀 ADCRH 暫存器」是硬體操作。
> 分得越乾淨,可以在電腦上測的部分就越多。

---

## 7.4 一鍵回歸測試

改完共用檔後,最怕「修好 A、弄壞 B」。用頂層的 `make test` 一次把關:

```bash
make test        # = 主機端單元測試 + 編譯全部範例
```

它背後跑的是 [`tools/build_all.sh`](../tools/build_all.sh),逐課編譯並回報 `[ OK ]` / `[FAIL]`。
只要有任何一課失敗,離開碼就是非 0,CI 會據此判定失敗(見 §7.9)。

## 7.5 第 ⑤.5 步:指令級模擬 ─ 在電腦上跑真正的 HEX

§7.3 測的是「不碰硬體的純邏輯」。但有些東西非得硬體才驗得出來:
Timer 的預載值對不對?SFR 設定有沒有寫錯?跳躍表跳對了嗎?

好消息:**SDCC 附帶一個 8051 指令級模擬器 `s51`**(ucsim 專案),
裝好 SDCC 就有了,可以直接執行你編出來的 `.hex`:

```bash
s51 -t 51 -X 16M -c - main.hex      # -t 51 = 8051  -X 16M = 時脈 16MHz
```

`-c -` 是「把指令控制台接到標準輸入」,所以可以用管線餵指令、把流程寫成腳本。

### 最常用的五個指令

| 指令 | 作用 |
|------|------|
| `step 500 ms` | 模擬「500 毫秒的執行時間」(也可用 `s`、`us`,或不加單位 = 指令數) |
| `dump sfr 0x90 0x90` | 看 SFR。`0x90` = P1,**一個位元組就是 P1 上八支腳的狀態** |
| `dump iram 0x30 0x33` | 看內部 RAM(你自己配置的變數) |
| `set memory iram 0x09 0x01` | 寫一個位元組進 RAM(用來「假造」一個輸入) |
| `set bit 0x00 1` | 設一個可定址的位元(⚠️ 不是 `set memory bit`,那個無效) |

### 例:把第 7 課的組語版跑一輪

```bash
cd asm/07-fsm && make
printf 'step 1 ms\nset bit 0x00 1\nstep 55 s\ndump sfr 0x90 0x90\nquit\n' \
  | s51 -t 51 -X 16M -c - main.hex
```

`set bit 0x00 1` 直接把 `request`(行人請求)位元設起來,等於「有人按過按鈕」——
這樣就不必去模擬按鈕的電氣行為。然後 `dump sfr 0x90 0x90` 看燈號:

```
0x90 P1:   0b01101000 0x68 'h' 104
```

`0x68` 怎麼讀?對照 `out_table`:bit3 = 車道綠、bit6 = 行人紅、bit5 = 按鈕腳維持 1
→ 車道綠燈 + 行人紅燈,正確。

### 例:把 UART 輸出存成檔案

模擬器可以把晶片送出的序列埠資料接到檔案,**連 USB-TTL 都不用**:

```bash
s51 -t 51 -X 16M -S out=/tmp/uart.txt -c - main_full.hex
cat /tmp/uart.txt
```

```
=== N76E003 Pedestrian Crossing (ASM) ===
Press P1.5 to request crossing
-> VEH GREEN
-> VEH YELLOW
-> PED WALK
-> PED FLASH
-> ALL RED
-> VEH GREEN
```

這一招對「字串表、查表、格式化輸出」特別有用 —— 只要有一個位元組算錯,
印出來就會錯行或變亂碼,一眼就看得出來。

### ⚠️ 最重要的一個陷阱:模擬器的時間會慢 12 倍

你會發現「本來 5 秒的綠燈,在模擬器裡要跑 60 秒」。這**不是你的程式有 bug**:

- 傳統 8051 的計時器吃的是 **Fosc / 12**。
- N76E003 是 **1T** 的 8051,而且我們在程式裡設了 `CKCON.T0M = 1`,
  讓 Timer0 直接吃**完整的 16MHz**(見 [`04-計時器與中斷.md`](04-計時器與中斷.md))。
- `s51` 模擬的是**傳統 12 分頻**的 8051,它**不認識 N76E003 的 `CKCON`** ——
  所以模擬器裡的計時器比實機慢了正好 12 倍。

**怎麼辦?** 兩個做法:

1. **把時間乘 12 來看**:實機 5 秒 → 模擬器下 `step 60 s`。(本章的例子就是這樣算的)
2. 只用模擬器驗「邏輯與順序」,時間的精準度留給實機用碼表驗(§7.6)。

> 同理,`s51` 也不會模擬 N76E003 特有的 PWM、ADC 等周邊。
> **模擬器驗得了「程式邏輯、SFR 操作、查表、字串」,驗不了「晶片特有的周邊行為」。**
> 它是實機測試的「前置篩檢」,不是替代品。

## 7.7 第 ⑦ 步:實機測試 ─ 每一課怎麼驗?

實機測試就是「確認晶片的行為符合預期」。不同課用不同的「觀測工具」:

| 課程 | 怎麼測 | 預期(通過標準)| 觀測工具 |
|------|--------|----------------|----------|
| 01 blink | 看 LED | 穩定閃爍、亮滅時間差不多 | 肉眼 |
| 02 button | 按/放按鈕 | 按下亮、放開滅,反應即時 | 肉眼 |
| 03 timer | 看 LED + 碼表 | 每 0.5 秒翻轉,10 次約 5 秒 | 碼表 / 手機馬表 |
| 04 uart | 看終端機 | 每秒一行、文字正確、count 遞增 | 序列埠終端機 |
| 05 adc | 轉旋鈕看數字 | 0↔4095 之間連續變化、兩端到底 | 序列埠終端機 |
| 06 pwm | 看 LED | 平滑呼吸(漸亮→漸暗循環),無明顯閃爍 | 肉眼 / 示波器看波形 |
| 07 fsm | 按按鈕 + 看終端機 | 綠燈未滿 5 秒時按 → 印「記下請求」、燈不變;滿 5 秒才切換;流程中按 → 印「忽略事件」 | 肉眼 + 序列埠終端機 |

**進階觀測工具**(有的話更好,沒有也能學):
- **萬用電表**:量腳位電壓(高≈3.3V、低≈0V)、量 ADC 輸入電壓對照讀值。
- **邏輯分析儀 / 示波器**:看 UART 波形、量 Timer 週期是否精準到微秒。

> UART 本身就是最好的「軟體觀測工具」:把你懷疑的變數 `uart_puts` 出來看,就知道程式跑到哪、值是多少。

## 7.8 除錯技巧(第 ⑦ 步不通過時)

當行為不如預期,依序檢查:

1. **程式真的燒進去了嗎?** 重燒一次、確認 `make flash` 沒報錯。
2. **接線對嗎?** 腳位有沒有插錯、GND 有沒有共接、LED 極性/按鈕位置。
3. **SFR 設定對嗎?** 這是最常見的錯:
   - GPIO 模式(`PxM1`/`PxM2`)有沒有設對?(驅動 LED 要推挽)
   - 中斷:`EA` 和對應的分開關(如 `ET0`)**兩個都開了嗎**?
   - UART:鮑率兩邊一致嗎?`TI` 有沒有忘記清?
4. **用 UART 印出來看**:在可疑的地方插 `uart_puts("reached A\r\n");`,或印出變數值。這叫 **printf 除錯法**,是最實用的手段。
5. **二分法**:把程式砍半,先確認前半段對,再逐步加回後半段,快速縮小問題範圍。

常見錯誤對照:

| 症狀 | 很可能的原因 |
|------|-------------|
| LED 完全不亮 | 沒設推挽輸出 / 接線 / LED 極性 / 腳位設錯 |
| LED 一直亮不閃 | 延時太短(快到看不出)/ 迴圈被最佳化(忘了 `volatile`)|
| 中斷不觸發 | 忘了開 `EA` 或分開關 / 忘了 `TR0` 啟動 |
| 中斷只進一次 | ISR 用了 `ret` 而非 `reti` / 16 位元沒重載 |
| UART 全是亂碼 | 鮑率不一致 / 接線 TXD↔RX 接錯 |
| UART 沒反應 | 忘了啟動 Timer1(`TR1`)/ 忘了清 `TI` |

## 7.9 第 ⑧ 步:版本控制(git)

每完成一個「可運作的里程碑」就提交一次,日後要回頭很方便:

```bash
git add -A
git commit -m "完成第 3 課:Timer0 中斷精準閃爍"
git push
```

**commit 訊息慣例**:用一句話講清楚「這次做了什麼」,動詞開頭、具體。
好:`修正 UART 鮑率計算,9600 下誤差降到 0.16%`;
不好:`update`、`修改一些東西`。

### 提交前自測:用本機回歸把關(可選 git hook)

`git push` 前先在本機跑一次 `make test`,確保沒有把任何範例改壞。
想自動化的話,可以設一個 git **pre-commit hook**,在每次 commit 前自動執行:

```bash
# 建立 .git/hooks/pre-commit 並加上執行權限
cat > .git/hooks/pre-commit <<'EOF'
#!/bin/sh
make test || { echo "make test 失敗,已取消這次 commit"; exit 1; }
EOF
chmod +x .git/hooks/pre-commit
```

這樣只要 `make test` 沒過,commit 就會被擋下來,避免把壞掉的程式提交進版本庫。

## 7.10 小結:一張流程卡

```
寫程式  →  make        (編得過嗎?)
        →  make test   (邏輯對嗎?在電腦上秒驗)
        →  s51 …       (選用:在電腦上跑真的 HEX,見 §7.5)
        →  make flash  (燒進晶片)
        →  實機測試     (行為對嗎?對照 §7.7 的通過標準)
        →  不對?用 §7.8 的技巧除錯
        →  對了?git commit / push(push 前記得先 make test 把關)
```

把這套流程走順,你就具備了開發任何嵌入式專案的基本紀律。🎉
